# Audit: mesh-output (Mesh from Implicit Body, View Mesh, Mesh from CAD, Reduce Mesh, Merge Meshes, Export Mesh, Preview Image)

Scripts and raw outputs: `SCRATCH/audit/mesh-output/` (t1 .. t16, `*_out.txt`; exported test files in `out/`).
All runs went through guard.py (CPU only, <= 1.8 GB peak), in-process `Evaluator(workers=1)`, samples `test_part.step` / `two_blocks.step`, voxels 0.3-1.2 mm.
Nothing in the repo was touched (a relative-path probe was run with the cwd moved into SCRATCH).
Not tested: the GPU paths (rules forbid `--gpu`), the real editor / WebSocket / frontend rendering, grids above ~5M voxels with real block counts (blocks were forced on small bodies instead), multi-worker pools.

## What was verified to work (so you do not need to re-check it)

- Block meshing is exact. t2: `tiles.TILE_MIN_VOXELS` lowered to 1000 and `BLOCK` = 96/36/24 on test_part (plain and with a 0.4 mm ridged wave texture), voxel 0.5 and 0.3: vertex count, triangle count and volume equal the whole-grid mesh (e.g. 92156 V / 184312 F both; volume diff <= 0.002 mm3; max vertex distance 4e-6 mm), 0 open edges, 0 non-manifold edges, 0 duplicate float32 vertices. 173 of 210 blocks computed at BLOCK=24, no holes.
- `tolerance` / `keep` in blocks: still watertight (whole 7527 V vs tiled-24 11608 V for tolerance 0.02: more triangles because every block keeps its border, expected; keep 0.3 -> 63666 vs 63556 F).
- STL reload from disk (float32 + merge by position, t11): every route is closed with 1 body and 0 bad edges: keep 1, keep 0.3, tolerance 0.02, tolerance 0.002, tiled keep/tolerance, Reduce Mesh node, Merge fuse=yes (textured body + CAD part). Only `Merge fuse=no` with the cracked CAD part has 8 bad edges (the CAD cracks, see below).
- Volume accuracy of marching cubes on the offset test part (CAD volume 32128 mm3): voxel 1.0 -> 31994 (-0.42 %), 0.5 -> 32093 (-0.11 %), 0.3 -> 32119 (-0.03 %). Offset +0.5 / -0.5 / +1 give the expected growth/shrink and bounds (-0.5 .. 60.5 etc.). So Draft (x4) loses about 0.4-1 % volume on this part: fine.
- `tolerance` is conservative (t5): on the textured test body (212k triangles) measured max deviation from the full mesh was 0.0042 mm at tolerance 0.01 (0.4x), 0.0077 at 0.02, 0.0365 at 0.1, 0.74 at 5.0 (always <= 0.55x the tolerance; the doc's "up to ~2x" never happened). 212k -> 17.8k triangles at 0.01. `Mesh from Implicit Body.tolerance` and `Reduce Mesh` give identical meshes (15054 F at 0.02). `tolerance` > 0 really replaces `keep` (tolerance 0.02 + keep 0.3 == tolerance 0.02 alone).
- `keep` is honoured: 0.5 -> 50.0 %, 0.3 -> 30.0 %, 0.1 -> 10.0 %, max deviation 0.0027 mm at 0.1.
- Build for previews (`server.build_run_graph`): Draft/Medium/Final multipliers 4/2/1 on a literal voxel; `keep` -> 1 and `tolerance` -> 0 below Final; `Merge fuse` -> no below Final. All as documented.
- Errors that are clear: body with no bounds ("cannot tell where this body is; connect a Domain"; View Mesh gives a longer, good message), voxel <= 0 ("voxel size must be greater than 0"), too-fine voxel ("grid too large (54 billion voxels); increase the voxel size" - refuses before allocating anything, limit `MAX_TILED_VOXELS` 30e9), not enough RAM for whole-grid meshing (with `available_memory` monkeypatched: "this needs about 0.1 GB of memory but only 0.0 GB is free..."), `Reduce Mesh` tolerance <= 0, `fuse` of an open mesh ("mesh 1 of 2 is not closed (NotManifold), so it cannot be fused").
- Preview Image works headless (VTK off-screen) in-process, writes a real 1400x1000 PNG, creates missing folders, accepts a list of meshes.
- Export formats: .stl .obj .ply .off work and reload watertight (OBJ/PLY/OFF drop the CAD per-triangle data without error); the chunked STL writer uses a constant ~150 MB extra at 1.3M triangles; OBJ ~100 MB per million triangles (13M-triangle lamp -> ~1.3 GB extra: acceptable); PLY ~24 MB per million.
- Block-meshing code read through (probe spacing, LIPSCHITZ 2.5, neighbour pull-in, edge-key welding): no defect found. Note `MAX_VOXELS` (300M) check in `_mesh` can never fire (`TILE_MIN_VOXELS` 32M is hit first): dead code, harmless.

## Findings

### [BUG] Export Mesh: .3mf export always fails ("No module named 'lxml'"), although the node and the file picker offer .3mf
Severity: medium (high if the user prints from 3MF) · Status: VERIFIED
Evidence: `t3_export.py` / `t3_out.txt`: `export implicit -> 'a.3mf' ERROR GraphError: node 'exp' (Export Mesh) failed: No module named 'lxml'` (same for a CAD mesh). `engine/graph/nodes.py:704` doc says ".stl, .3mf, .obj or .ply", `frontend/src/components/EngineNode.tsx:162` offers `.3mf` in the save dialog, `requirements.txt` has plain `trimesh` (no lxml; trimesh's `export_3MF` imports lxml, confirmed missing in the `synkad` env). The error also only appears when the Export node runs, i.e. after the whole graph has been computed (minutes for the lamp).
Why it matters to the user: a designer who picks the .3mf format (Bambu/Prusa slicers prefer it) loses a long export run to an install problem, and the message does not say what to do.
Suggestion: add `lxml` to requirements.txt (and install it in the env); or catch ImportError in `meshing.export` and say "3MF export needs the lxml package: pip install lxml". Better, check this before computing anything (see the pre-validation finding below). For a list of meshes a 3MF could also keep each part as its own object.

### [BUG] Mesh from Implicit Body / View Mesh: a body that grows beyond Padding is silently cut flat; the 3D preview of any implicit node cannot be given more padding and is clipped differently in Draft and Final
Severity: medium-high (silent wrong result for textures with amplitude > ~2 mm) · Status: VERIFIED
Evidence: t16 (`t16_clip.py`): test_part offset by a ridged wave x 4 mm (distance field `range` = (-4, 4)), but the Offset Body's `bounds` stay the plain part box (0..60, 0..40, 0..15; `fields.py:199` "body - distance keeps the body's bounds"). Mesh from Implicit Body with Padding 2.0, voxel 0.5: mesh closed and "fine" but volume 31765 mm3 vs 32082 mm3 with Padding 4.5; bounds are cut at -3.04 / 63.04 instead of -4 / 64; 3308 grid-boundary samples are inside the body (the mesh has flat caps on four grid planes). t1: offset +3 mm, padding 0, voxel 0.5 -> mesh bounds -1.142..61.142 (should reach -3..63), volume 43994 mm3, no message. `server.build_run_graph` builds the preview `mesh.view` node with no padding input (`nodes.py:609` default 2.0, not editable): t8 shows the eye-preview of that same offset body clipped at -3.04 in Draft but -2.27 in Final (cells 128 vs 512 change the "+2 voxels" margin), so Draft and Final previews show different amounts of the texture and neither shows it all. The port doc ("At least the largest outward offset, or the surface gets cut off") is correct but nothing checks it.
Why it matters to the user: "my texture looks cut off / flat on top" is exactly the kind of "something isn't working" a designer meets when raising an amplitude; the mesh is watertight and exports fine, so there is no sign anything is wrong, and the preview of a body node cannot be fixed from the UI.
Suggestion (small): (1) in `fields.offset`, when the distance field has a known `range` (interval arithmetic already gives (-4, 4) here), grow the result's `bounds` by max(0, range_hi); (2) in `_mesh` / `_mesh_on` / `tiles` (cheap): after evaluating, if the field is < 0 anywhere on the outer shell of the grid, `report_message` "The body is cut off by the meshing grid: increase Padding to at least X mm" (X could be estimated from the extent of the negative samples near the boundary); (3) let `mesh.view` take its padding from the largest `padding` among the graph's Mesh from Implicit nodes or add 10 % of the body size.
Also: the effective margin is `padding + 2 * voxel` (`Grid.from_bounds`), so "Extra room around the body, mm" understates it (harmless).

### [BUG] build_run_graph: a Voxel that is wired from a Number node (or a group setting) is never multiplied, so Draft/Medium previews run at full resolution
Severity: medium · Status: VERIFIED (build_run_graph output), consequences SUSPECTED
Evidence: `server.py:111-112` `if not _is_link(voxel): inputs["voxel"] = float(voxel) * multiplier`. t8: with a literal voxel 0.4 the Draft graph has `voxel = 1.6`; with `voxel` linked to an `input.number` the Draft graph still has `{'link': 'vox.out'}` (evaluated at the Number's value). Group settings are Number nodes too (`core`/`graphConvert`: "Number nodes inside are the group's settings"), and `Graph.from_dict` expands groups before `build_run_graph`, so a Mesh node inside a group whose voxel is a group setting is also never scaled. The user's current recipes use literal voxels, so this has not bitten yet, but it is the natural way to drive "one voxel size for the whole graph".
Why it matters to the user: wiring one Number into several Mesh nodes (the tooltip on the Number node recommends exactly that) silently turns Draft into a full-resolution run; on the lamp that means hours and GBs instead of seconds, and the preview toolbar says Draft.
Suggestion: apply the multiplier in the evaluator instead: add a hidden `quality_scale` input (like `compute`/`stamp` in `_set_compute`) to `mesh.from_implicit`, set by `build_run_graph`, and multiply inside the node (`voxel * quality_scale`), so links work. Or resolve links to Number nodes in `build_run_graph` (follow `link` to an `input.number`, scale the node's copy).

### [BUG] Reduce Mesh (and meshing.reduce with snap=True): a mesh with open edges is returned unchanged; cracked CAD meshes are reduced only partly
Severity: low-medium · Status: VERIFIED
Evidence: `t6_open.py`: an open icosphere (4604 faces, 68 open edges): `meshing.reduce(V, F, 0.2)` returns 4604 faces (no reduction), while `snap=False` gives 1090 faces and a float32-representable input also gives 1090. Cause: `meshing.reduce` (line ~197-199) tests whether leftover single-use edges were open in the input by comparing exact float64 coordinates (`_keys(V[_open_vertices(F)])`) with the output vertices, which `_reduce_rest(..., snap=True)` has already snapped to float32, so no open edge ever matches; every round counts the border as a "problem", freezes more triangles (radius doubling) and after 4 rounds the input comes back ("nothing could be removed safely"). The tiled path uses `snap=False`, which is why blocks work. Real-world effect (t5b, t13): `Mesh from CAD` of test_part (8 crack edges) 3852 -> 3152 triangles only around the cracks (output is closed, 0 bad edges, max deviation 0.003 mm), and an unfused `Merge` of textured body + CAD part reduced 216k -> 17.7k (fine); only a mesh with a large open border is hit.
Why it matters to the user: Reduce Mesh promises "watertight, every edge shared by exactly two triangles" and says "nothing could be removed safely" when the real reason is a float32 key mismatch; on an open input the message is misleading.
Suggestion: compare keys in the same space (`_keys` of `V[open].astype(float32)` when `snap`), or snap the input first. Also say in the message when the input has open edges ("the mesh has open edges, it was left as it is").

### [UX] Draft/Medium previews of thin features (0.6 mm walls, sheet lattices) are badly wrong and nothing tells the user
Severity: medium · Status: VERIFIED
Evidence: `t15_shell.py` (test_part Shell 0.6 mm, recipe voxel 0.3): true volume ~4529 mm3; Final 4525, Medium (0.6 mm voxel) 3477 (-23 %), Draft (1.2 mm voxel) 1146 (-75 %, 7 components). Shell 1.5 mm: Final 11310, Medium 11309, Draft 10727 (-5 %). `t8_quality.py` (0.6 mm gyroid sheet, cell 5): Final 10992 mm3 / 8 components, Medium 9956 / 24, Draft 1620 mm3 / 1508 components (the lattice shatters into specks). A 0.4 mm slab at voxel 0.2 does not mesh at all ("Field has no surface inside the grid (no sign change)"). The only hint is the toolbar tooltip `Toolbar.tsx:259` "Draft is 4x coarser than the recipe, Medium 2x."
Why it matters to the user: lattices and thin shells are exactly what is being tested; a Draft preview of a 0.6 mm sheet lattice looks like random debris and suggests the node is broken. The same hint is missing for "no decimation / no fuse in previews".
Suggestion: (1) cheap generic warning in `_mesh`: when the preview multiplier != 1 and any field in the tree declares a minimum feature (TPMS/strut/voronoi thickness, shell thickness, offset magnitude; add an optional `min_feature` attribute to `Field`), report "Draft voxel 1.2 mm is larger than half the thinnest feature (0.6 mm): thin walls will be missing, use Medium/Final"; (2) or clamp the preview voxel to `min_feature / 2` when that is affordable; (3) extend the tooltip: "Draft/Medium also skip Keep/Tolerance and Merge fuse; walls thinner than ~2 voxels may vanish".

### [UX] Mesh from Implicit Body: "Field has no surface inside the grid (no sign change)" is cryptic for an empty or too-thin body
Severity: low-medium · Status: VERIFIED
Evidence: `t9_errors.py`: body minus itself, offset -50, offset -7.4 and -7.6 on the 15 mm test part at voxel 0.5 (a 0.2 mm slab), voxel 30 and 100 all give the same text (`meshing.py:13`). Only the first cases are really "empty"; the slab and the big voxel cases are "thinner / smaller than the voxel".
Suggestion: say what to try and what the field looked like: "Nothing to mesh: the body is empty, or thinner than one voxel (0.5 mm) - try a smaller Voxel. Field range -0.12 .. 3.4 mm". The View Mesh preview can add the same hint since Draft makes this case far more likely.

### [UX] Export Mesh: wrong or missing file extension gives a garbled message, and path problems only show after the whole graph has run
Severity: low-medium · Status: VERIFIED
Evidence: `t3_out.txt`: `.step`, `.stl.txt`, no extension, empty path all give `node 'exp' (Export Mesh) failed: ('%s exporter not available!', 'step')` (a trimesh ValueError printed as a tuple; for a path without extension the "format" shown is the whole path). The node runs last, so a typo, a read-only folder, a locked file (STL open in the slicer) or the missing lxml are discovered after every upstream node has been computed (the lamp: minutes). The file is also written in place (not to a temp file + rename), so a failed/cancelled write leaves a truncated STL where the previous good export was.
Suggestion: add an optional per-node `check(inputs)` hook that `Graph.problems()` calls (before any compute) with: extension in {stl, obj, ply, off, 3mf} (and lxml importable for 3mf), folder creatable, existing file not locked (open for append and close). Report as "Export Mesh: path: unsupported file type '.step' (use .stl, .3mf, .obj or .ply)". Write to `path + '.tmp'` then `os.replace`.

### [UX] Export Mesh / Preview Image: a relative path lands in the server's working directory, the log shows only the relative text, and files are overwritten silently
Severity: low · Status: VERIFIED
Evidence: t3: `path = "audit_rel_probe.stl"` was created in the process cwd (`os.getcwd()`), the node returns `str(path)` as given (`nodes.py:710`), the editor logs `Exported samples/test_part_wave.stl` (`store.ts:457`). `start.bat` does `cd /d "%~dp0"`, so these end up inside the repo folder (default node path `out.stl`, toolbar template `samples/out.stl`). Second export to the same path overwrites without a word; `recipes/lamp_noise.json` and `lamp_noise2.json` both write `samples/lamp_noise.stl` and `.png`, so exporting one design replaces the other design's file.
Suggestion: return and log the absolute path (`Path(path).resolve()`), and add the size and triangle count to the log line ("Exported C:\...\lamp_noise.stl: 8.5 M triangles, 425 MB"). Optional: an `overwrite` choice (yes / add number) or a `{recipe}` / `{date}` token in the path; resolve relative paths against the recipe's folder.

### [UX] Mesh from CAD: output is not guaranteed watertight, and neither Export nor the node say so
Severity: low-medium · Status: VERIFIED
Evidence: t3/t4: test_part's CAD mesh (OpenCascade T-junction cracks at the fillets) exported to STL reloads with 8 open edges and 8 over-used edges, 9 "bodies" (`wt False`); the exported lamp-style `Merge fuse=no` of textured body + CAD part has the same 8 bad edges. `Mesh from CAD` simply returns the Import STEP mesh (`nodes.py:638-641`), the doc only says "exact and instant". Side finding: `Merge Meshes` with `fuse = yes` of that one CAD mesh gives a closed 1-body mesh (3844 F, volume 32128.004) and `Reduce Mesh` also closes it, so there are two accidental repairs; only the user who knows this gets a closed STL.
Suggestion: have `export_mesh` count open/over-used edges (np.unique over edges, skip above ~3M triangles or sample) and put "Export: 8 open edges (CAD cracks); a Merge Meshes with fuse = yes closes them" in the log; or add a `repair` choice to Mesh from CAD that welds T-junctions (the manifold3d `merge()` pass already does it).

### [UX] Merge Meshes: fuse defaults to "yes", the 1 mm3 speck limit is hard-coded and small separate parts are dropped; intentional separate solids are reported as an error
Severity: low · Status: VERIFIED (function level, t4)
Evidence: `meshing.fuse`: big body + a separate 0.73 mm3 piece -> piece dropped ("specks dropped 1"; only an info line in the log); `SPECK_VOLUME = 1.0` mm3 is fixed even for a 5 mm part where 1 mm3 is a real feature; `merge_meshes` logs "N meshes gave M separate solids; parts that do not overlap stay separate" at level "error" even when the user wants separate parts (a print plate). Exactly coincident touching faces do fuse (two 10 mm boxes sharing a face: 1 piece, 2000 mm3), but boxes touching only along an edge give a non-manifold result (2 pieces, `wt False`) and a gap of 0.01 mm gives 2 pieces: "touching is not enough" in the doc is right for meshed bodies (each marching-cubes surface is ~0.005 mm inside the shared plane: `two_blocks` meshed at 0.5 mm -> 2 solids, as logged) but the opposite for CAD meshes. A preview (fuse = no) can therefore look fine while the Final/export fails (open input mesh -> "mesh 1 of 2 is not closed (NotManifold)") or drops specks.
Suggestion: expose `speck volume` (default 1, 0 = keep everything) and report dropped parts' volume; log "separate solids" at info level unless fuse was asked for a single solid; mention in the Merge doc that Draft/Medium never fuse so errors only show at Final.

### [IMPROVEMENT] Mesh nodes give no readout of what they made (triangles, volume, size, watertight)
Severity: low · Status: SUSPECTED (UI code: nodes only report `note` via `_output_extras`, mesh nodes set none)
Suggestion: set a `note` on Mesh from Implicit Body / Reduce Mesh / Merge Meshes outputs ("1.31 M triangles, 31 831 mm3, 60.8 x 40.8 x 15.8 mm"); Reduce Mesh should always log "kept 17766 of 212224 triangles (8.4 %)" not just the failure case; add the same line to the Export log. These also make the effect of Keep/Tolerance/Draft visible.

### [IMPROVEMENT] Keep / Tolerance accept values that silently do something else
Severity: low · Status: VERIFIED
Evidence: t5: `keep` 0.0 and -1 -> same as the maximum reduction (6876 F = 3.2 %, the collapse stops by itself), `keep` 2 -> no reduction (no message); Mesh from Implicit `tolerance` -0.01 is ignored and Keep applies instead; `Reduce Mesh` tolerance <= 0 gives a clear error but Mesh from Implicit's tolerance does not.
Suggestion: clamp/raise for keep outside (0, 1] and negative tolerance; log the achieved share when the target could not be reached.

### [IMPROVEMENT] Reduce Mesh is not skipped in Draft/Medium previews although Keep/Tolerance of Mesh from Implicit Body are
Severity: low · Status: SUSPECTED (code: `build_run_graph` only resets `mesh.from_implicit`)
Evidence: `server.py:113-115` comment "decimation only matters for the files you export"; `mesh.reduce` is not special-cased, so a Reduce Mesh node runs at every preview with the same tolerance (0.4 s at 212k triangles; ~28 s per 5.7M triangles at Final according to its doc).
Suggestion: make `mesh.reduce` pass through below Final, like Keep/Tolerance (and say so in its doc).

### [IMPROVEMENT] Export runs also compute the previews of every visible node at Final quality
Severity: low · Status: SUSPECTED (code)
Evidence: `build_run_graph` walks `visible` in "export" mode too and, for an implicit body with the eye on, adds a `mesh.view` node with `cells` = 512 (up to 134M voxels, block-meshed) next to the real Mesh from Implicit Body.
Suggestion: in export mode skip the views of nodes that are not needed by an export node (or keep only the views of meshes that already exist).

### [IMPROVEMENT] Preview Image: sharp edges are smeared, fixed camera and size
Severity: low · Status: VERIFIED (render of two_blocks: the flat boxes look like pillows)
Evidence: `engine/preview.py:24` `normals.SplittingOff()` averages normals across 90 degree edges; `render()` has a fixed 1400x1000 size and one camera; a path ending in `.jpg` or with no extension still gets PNG data.
Suggestion: feature-angle splitting (e.g. 50 degrees; `vtkPolyDataNormals.SplittingOn()` + `SetFeatureAngle`) for meshes below ~2M triangles; optional size / view (iso, front, top) inputs; force a `.png` extension or warn.

### [INFO] Smaller notes
- A list of bodies plus a single `domain` crops every body to the domain's box without a message (t10: second block of two_blocks keeps 1741 of 23959 mm3). CLAUDE.md already warns about the cost; a note "N bodies extend outside the domain" would catch it.
- Draft (voxel x4) of a body list and Smoothen: `smoothen` sigma is in mm, so a sigma below 0.05 voxel is skipped; at a 4x coarser voxel the default Smoothen (grid 0.1 mm, 3 passes, sigma 0.14 mm) is 0.35 voxel in Draft: little effect, so Draft looks sharper than Final here (not tested further; Smoothen belongs to the implicit-lattice area).
- `Mesh from Implicit Body` shows no parallel progress for a single big body except the "Meshed in blocks" message; fine.
